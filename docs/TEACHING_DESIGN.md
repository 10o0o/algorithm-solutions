# 알고리즘 수업 개선 설계

**2026-10-23 운영 문서 반영·구현 검증 완료.** 점검 당시 수업은 설명·교정 뒤 다음 문제로 이동하는 데 비해, 도움을 줄인 적용과 나중의 독립 해결을 관찰하는 연결이 약했다. 개선의 중심은 실제 코드에서 막힌 단계를 구분하고, 그 단계에 필요한 도움을 준 뒤 학습자에게 전체 풀이를 돌려주는 것이다.

수업 대응은 [학습 스킬](../.agents/skills/study-algorithms/SKILL.md), 선택 기준과 기존 예산은 [로드맵](../ROADMAP.md), 중단 상태와 재개 선택은 [STATE](../STATE.md)에 반영했다. 범위와 실제 검증 결과는 [구현 계획의 실행 결과](TEACHING_IMPLEMENTATION_PLAN.md#실행-결과)에 둔다. 사용자 학습은 계속 중단 상태이며, 실제 학습 효과는 아직 관찰하지 않았다.

## 판단의 범위

평가 대상은 이 대화에서 확인한 수업, 현재 코드, [학습 진행 검토](LEARNING_REVIEW.md), [현재 학습 스킬](../.agents/skills/study-algorithms/SKILL.md)이다. 진행 검토와 문제 복기는 같은 대화를 정리한 자료이므로 독립적인 관찰 표본으로 중복 계산하지 않는다.

확인한 성과에는 SCC의 위상순서에 대한 사용자 설명, 사용자 구현과 수정, 사용자 보고 AC 네 건이 있다. 코드의 로컬 통과는 구현 검증이며, 별도 날짜의 기억·새 문제 접근 선택·대회 성과와 구분한다. 실제 학습 시간과 독립 작업 비중은 미측정이므로 효율 저하의 크기, 진도 속도, 목표 달성 시점을 계산하지 않는다.

이번 설계가 다루는 질문은 다섯 가지다. 무엇이 실제 병목이었는지, 어떤 설명 깊이가 필요한지, 상황별 도움을 어떻게 조절할지, 과제 선택을 목표에 어떻게 연결할지, 개선 여부를 어떤 작은 관찰로 확인할지다.

## 실제 사례와 원인

| 관찰한 사례 | 판단과 원인 추정 | 수업에 미친 영향 | 개선 우선순위 |
| --- | --- | --- | --- |
| SCC에서 사용자가 자신이 만든 코드가 아니어서 무슨 문제를 푸는지도 모르겠다고 말했다. | 문제의 목적·구체적인 동작과 제공된 구현의 연결이 부족했다. 코드 진행이 학습자의 이해보다 앞섰다는 직접 신호다. | 구현 단계가 늘어도 전체 풀이를 소유하기 어려웠다. | 최우선: 작은 사례에서 목적과 데이터 흐름을 다시 연결한다. |
| [Printing Machine](../atcoder/abc325d.md)에서 실행 가능 시간 범위를 전체 점유 구간처럼 처리했고, 정렬·조건 수정이 이어졌다. | 핵심 병목은 문제 모델이었다. 이 혼동을 정렬 기준의 문제로만 다루면 수정이 반복된다. | 회의 배정과 시간별 후보 선택의 차이를 익히기 전에 구현을 계속 고치게 됐다. | 최우선: 시간표와 가능한 행동부터 설명한다. |
| [LCS](../atcoder/dpf.md), [Packing](../atcoder/abc214e.md)은 요청에 따라 모범 코드를 제공했다. | 예제 학습은 정당하다. 이후 자료 없는 적용 근거는 부족하다. 모범 코드 제공 자체를 실패로 판단하지 않는다. | 설명을 따라 이해한 것과 스스로 구성하는 능력을 구분할 기회가 적었다. | 높음: 후속 적용에서 제공하는 도움을 줄인다. |
| [Querying Multiset](../atcoder/abc212d.md)의 삽입 보정은 한 줄 수정이었다. | 수정량은 작지만 `실제 값 = 저장값 + add`라는 풀이의 핵심이었다. | 줄 수만 보고 사소한 수정으로 넘기면 중요한 학습 기회를 놓친다. | 높음: 수정 중요도를 상태·불변식과의 관계로 판단한다. |
| [Flip Edge](../atcoder/abc395e.md), [Crystal Switches](../atcoder/abc277e.md)에서는 인접 목록 접근·거리 갱신·초기화·간선 방향을 교정했다. | 알려진 오류는 구현과 모델의 대응에 있다. 알고리즘 전체를 모른다는 진단으로 확대할 근거는 없다. | 새 그래프 이론을 더 설명해도 현재의 구현 오류는 그대로 남을 수 있다. | 높음: 상태 한 번의 실제 전이를 코드와 대응시킨다. |
| 주제와 기법을 설명한 뒤 구현하는 연습은 여러 번 있었으나, 별도 날짜 재현·태그 없는 혼합 측정은 확인하지 못했다. | 학습 방식이 주제별 안내에 치우쳤다. 독립 적용의 부족 정도는 아직 측정할 수 없다. | 풀이를 선택하는 능력과 지연된 기억을 관찰하기 어렵다. | 높음: 기존 예산 안에서 두 관찰 기회를 확보한다. |
| 입력·CPH 준비와 코드 가독성 검토도 있었다. | 사용자가 요청한 학습 지원이다. 큰 이탈의 증거는 없지만 지원 작업이 수업을 점유하지 않게 해야 한다. | 도구 문제가 반복되면 독립 풀이 시간이 줄어들 수 있다. 현재 손실 시간은 미측정이다. | 보통: 강사가 처리하고 간단한 실행 경로로 복귀한다. |

여러 사례를 연결하면, 강사가 현재 문제를 통과시키는 데 집중하면서 학습자가 어디까지 스스로 할 수 있는지에 맞춘 다음 선택이 약해졌다고 해석할 수 있다. 이는 수업 과정에 대한 원인 가설이며 학습자의 능력 저하가 입증됐다는 뜻은 아니다.

기존 스킬에는 이미 충분한 독립 과제, 작은 예제, 혼합 연습, 도움 구분 원칙이 있다. 따라서 같은 원칙을 길게 추가하는 것만으로는 재발을 막기 어렵다. 아래 설계는 실제 발화·코드·출력에 따라 강사가 취할 행동을 정한다.

## 유지할 점과 바꿀 점

SCC·DAG DP → DP → 이분탐색 → 누적합·스위핑 → 힙·그리디 → 최단경로·상태 그래프의 연결은 유지할 만하다. 주제 이동 순서 자체가 로드맵 이탈은 아니다. 사용자의 직접 구현, 실제 반례 리뷰, 요청 시 모범 코드 제공도 유지한다.

바꿀 부분은 설명의 단위, 막힘의 진단, 도움 뒤의 후속 적용, 다음 문제를 고르는 근거다. 모든 주제를 처음부터 다시 배우거나 모든 AC 문제를 재구현하는 방식은 채택하지 않는다.

| 평가 요구 | 설계상 대응 |
| --- | --- |
| 불필요한 깊이 방지 | 정확성·적용 조건·현재 병목에 연결되는 설명을 우선하고, 선택 심화는 필요할 때 다룬다. |
| 학습 밖 과제 방지 | 도구·저장소 운영은 강사가 처리한다. 학습자 과제는 풀이 설계·구현·실행·리뷰로 묶는다. |
| 목표와 커리큘럼 정합성 | 파랑 도달을 가까운 목표로 두고, ABC 올솔·노랑·Codeforces 장기 목표를 별도로 확인한다. |
| 로드맵 실행 개선 | 새로운 시간표를 더하지 않고 기존 주간 예산의 독립·혼합·재현 활동을 실제로 선택한다. |
| 진행 판단 개선 | 과제 수행, 받은 도움, 설명, 실행, 나중의 적용을 확인한 범위로만 판단한다. |

연구를 CP 수업에 적용한 구체적인 과제 수·시점·도움 기준은 운영 제안이다. 이 자료로 개인의 rating 상승량, 유일한 최적 복습 간격, 반드시 성공할 학습 비율을 정하지 않는다.

대안도 구분한다. 해설 중심 학습은 새 기법을 이해하는 데 유용하고, 독립 풀이 중심 학습은 이미 배운 내용을 선택·구현하는 데 필요하다. 모든 기법을 알고 푸는 방식과 처음부터 모든 문제를 무힌트로 버티는 방식 중 하나로 고정하지 않는다.

## 수업을 진행하는 기본 흐름

**현재 파일 확인 → 목표 하나와 이유 제시 → 필요한 설명 → 충분한 독립 작업 → 실제 코드·출력 리뷰 → 이동 또는 필요한 부분 보완.** 학습자가 이미 보여준 설명·실행은 다시 시험하지 않는다.

회차를 시작할 때 강사는 목표, 지금 선택한 이유, 완료 기준을 짧게 제시한다. 시간 질문은 배정에 실제로 필요할 때만 한다. 구현을 시작하기 위해 과거 실력·모든 풀이 이력·전체 커리큘럼을 다시 답하게 하지 않는다.

| 이번 수업의 목적 | 처음 제공할 것 | 학습자가 수행할 작업 | 강사가 확인할 것 |
| --- | --- | --- | --- |
| 새 기법 학습 | 문제의 목적, 작은 예제, 원리·적용 조건. 학습할 기법을 알려도 된다. | 전체 풀이 설계·구현·실행. 막힌 부분의 도움을 요청할 수 있다. | 어떤 부분을 스스로 구성했고 어떤 핵심 도움을 받았는지. |
| 혼합 연습 | 원문과 실행 준비. 강사가 덧붙이는 태그·추천 기법·알고리즘별 함수 틀은 감춘다. | 접근 선택부터 구현·검증까지 먼저 시도한다. | 선택 이유, 첫 접근, 도움 전후 변화. |
| 다른 날 재방문 | 선별한 과제와 확인 목적. 기법을 알려주는 재현과 기법을 숨기는 적용을 구분한다. | 자료 없는 재풀이 또는 새 변형 적용 중 하나를 수행한다. | 기억에서 구성한 부분, 새 조건에 맞춘 부분, 추가 도움. |
| 실전·측정용 virtual | 사전 노출과 공식 시간·규칙을 확인한다. | 제한 시간 동안 독립적으로 수행한다. | 종료 후 시간 배분·판정·미해결 원인. 진행 중 풀이 도움은 주지 않는다. |

혼합 연습에서도 원문 자체의 표현·제목을 임의로 바꾸지 않는다. 강사가 추가하는 설명과 준비 코드에서 해법이 새지 않게 한다. 과거 코드를 이동·삭제하거나 기존 노트를 숨김 처리하는 구현은 필요 없다.

## 막힌 단계에 따른 설명과 도움

강사가 먼저 현재 코드와 설명에서 판단한다. 증거만으로 구분할 수 없을 때만 막힌 지점에 관한 짧은 질문 하나를 한다. 아래 구분은 강사의 판단 도구이며 학습자가 매번 작성할 양식이 아니다.

| 관찰한 막힘 | 강사의 첫 행동 | 독립 작업으로 돌아갈 지점 |
| --- | --- | --- |
| 무엇을 구하는 문제인지 불분명함 | 입력 하나에서 허용되는 행동과 목표를 직접 보여준다. 기존 코드의 변수와 연결한다. | 문제의 의미에 맞는 전체 설계를 다시 시작할 수 있을 때. |
| 문제는 이해했지만 새 기법을 모름 | 원리·작은 예제·적용 조건을 연결해서 가르친다. 필요한 선수만 보완한다. | 해당 기법으로 기본 풀이를 구성할 수 있을 때. |
| 그리디·DP 등 접근의 근거가 불분명함 | 작은 사례에서 상태·선택을 비교한다. 잘못된 접근에는 반례를, 타당한 접근에는 필요한 논증을 연결한다. | 선택의 근거를 이해하고 전체 풀이를 구성할 수 있을 때. |
| 아이디어는 맞으나 코드가 상태 의미와 다름 | 한 번의 전이를 표로 추적하고 현재 줄과 대응시킨다. 관련 오류를 한 번의 리뷰에 묶는다. | 상태·전이에 맞는 수정 방향이 분명해졌을 때. |
| 인덱스·입출력·단순 문법만 막힘 | 필요한 문법이나 허용된 작은 수정을 처리한다. | 즉시 원래 과제로 돌아간다. 기초 과정 전체를 다시 시작하지 않는다. |
| 실행은 맞지만 적용 조건·복잡도가 불확실함 | 현재 풀이의 시간·공간과 필수 조건을 실제 제약에 연결한다. | 필요한 검토가 끝나면 이동한다. 관계없는 최적화까지 확장하지 않는다. |

같은 설명 뒤에도 이해가 어렵다는 반응이 나오면 표현을 바꾼다. 스케줄링은 시간표, DP는 작은 표, 그래프는 상태 두세 개의 이동으로 보여준다. 변수 이름만 바꿔 같은 추상 설명을 반복하지 않는다.

힌트·핵심 설명·부분 코드·전체 모범 코드는 상황에 맞게 고른다. 모든 도움 단계를 차례로 거치게 하지 않는다. 사용자가 정답을 요청하면 제공하고, 이해 흐름을 설명한다. 강제 재시험을 대가로 붙이지 않는다.

설명 깊이의 기준은 현재 문제를 정확하게 풀고 다음 적용을 이해하는 데 필요한가이다. 이분탐색의 진행 보장, DP 상태, 반열린 구간, 그리디 선택 근거, 최단경로 적용 조건은 우선한다. 행 별칭·문법 질문은 필요한 만큼 답한다. 선택적인 다른 알고리즘, 상수 최적화, 스타일 정리는 요청이나 실제 병목이 있을 때 다룬다.

## WA 리뷰와 코드 수정

`틀린 이유` 요청에는 저장된 최신 파일을 다시 읽는다. 현재 접근의 타당성을 먼저 검토하고, 의미 있는 작은 반례에서 기대값과 실제 출력을 확인한다. 참고 풀이와 표현이 달라도 같은 답을 보존하는 접근일 수 있다. 실행하지 않았으면 추적 결과라고 밝힌다. 첫 잘못된 판단·전이와 관련 오류를 한 번에 설명하며, 매 줄을 새 과제로 쪼개지 않는다.

| 수정의 성격 | 처리 기준 |
| --- | --- |
| 사소한 수정이 위임된 범위 | 강사가 수정·좁은 실행 검증 후 바뀐 점을 짧게 알린다. 같은 승인을 다시 요구하지 않는다. |
| 한 줄이지만 핵심 상태·불변식에 해당 | 의미와 반례를 함께 설명한다. 기본은 학습자 수정이며, 이미 확인된 대행 요청이 있으면 수정해도 도움의 핵심을 구분한다. |
| 접근·자료구조 전체의 변경 | 원인과 새 흐름을 설명한다. 완성 코드 교체는 사용자가 요청한 범위에서 한다. |
| 사용자도 같은 파일을 수정 중임 | 적용 직전에 해당 내용을 다시 읽는다. 충돌하거나 파일이 바뀌었으면 새 버전을 기준으로 재검토한다. 이전 버전 진단을 그대로 재적용하지 않는다. |

샘플과 원인을 가르는 반례를 우선한다. 복잡한 정확성 우려가 남을 때만 작은 완전탐색 비교나 추가 성능 검증을 선택한다. 모든 일반 풀이에 대규모 테스트 체계·회귀 테스트·프레임워크 리팩터링을 요구하지 않는다. 강사의 많은 테스트가 학습자의 이해를 대신하지 않는다.

## 다음 과제와 이동을 정하는 기준

강사는 현재 파일·설명·실행으로 확인된 공백을 먼저 적고, 그 공백 또는 목표와 연결되는 과제 하나를 고른다. 익숙한 도구를 쓰면서 새로운 판단을 연습하는 문제를 우선할 수 있다. 여러 핵심을 동시에 새로 배워야 해서 막히면 설명이나 연결 과제의 범위를 줄인다. 새 개념 하나는 선택을 돕는 경험칙이며 고정 입장 조건이 아니다.

| 현재 근거 | 다음 선택 |
| --- | --- |
| 새 원리를 설명받고 기본 구현을 마침 | 도움을 줄인 변형을 선택할 수 있다. 지금의 성공을 접근 선택 능력으로 확대하지 않는다. |
| 핵심 코드·설계를 많이 제공받음 | 필요한 과제를 선별해 다른 날 재현하거나 새 변형에 적용할 기회를 둔다. 모든 문제의 즉시 재구현을 요구하지 않는다. |
| 핵심 도움 없이 설계·구현하고 필요한 검토를 마침 | 다음 변형이나 다른 주제로 이동한다. 같은 기초 확인을 반복하지 않는다. |
| 비슷한 오개념이 반복됨 | 해당 모델·불변식만 작은 사례로 보완한다. 이미 배운 주제 전체를 초기화하지 않는다. |
| 사용자가 다음으로 이동하길 원함 | 확인한 성과를 인정하고 요청한 진행을 따른다. 미확인 범위를 짧게 남기며 강제 관문으로 붙잡지 않는다. |
| 독립 근거가 부족하지만 사용자가 직접 구현·수정한 성과가 있음 | 도움 후의 진전으로 인정한다. 모든 성과를 미완료로 돌리지 않는다. |

가까운 목표는 AtCoder 파랑 도달이다. 현재까지 다룬 T01·T03·T04·T05·T06과 힙 등 도구의 모델링·구현 안정성을 먼저 관찰하고, 미진행 범위는 실제 다음 과제의 선수와 정기 측정의 막힘에 따라 고른다. 고급 기법의 목록을 다음 과제 선정 이유로 쓰지 않는다. 노랑·ABC 실전 올솔·장기 Codeforces 목표는 서로를 달성했다는 근거로 대체하지 않는다.

현재 ABC277E의 전면 재구현은 한 선택지다. 상태·간선·초기화가 관련된 새 변형으로 적용을 확인하는 선택도 가능하다. 둘을 한 회차에 모두 부여하지 않는다. 보류한 출발·도착 고정 SCC 변형을 의무로 되살리지 않는다.

## 주간 예산과 지원 작업

시간 배정은 [기존 주간 운영](../ROADMAP.md#주간-운영과-점검)을 기준으로 한다. 혼합·재현·대회는 총 주 5–7시간 안의 활동이다. 재방문 과제가 생기면 새 분량을 줄이거나 기존 활동을 대체하고, 밀린 복습을 추가 숙제로 누적하지 않는다.

독립 시간은 학습자가 직접 설계·구현·실행·반례 검토를 한 시간이다. AI 설명·코드 작성·도구 대기 시간을 포함하지 않는다. 대화 메시지 사이의 시간은 휴식이나 다른 활동을 포함할 수 있으므로 순수 학습 시간으로 자동 계산하지 않는다. 실제 시간은 관찰·사용자 보고·근사·미측정을 구분한다.

CPH나 자동 입력이 막히면 강사가 필요한 설정을 처리한다. 해결이 길어지면 일반 실행과 샘플 입력으로 학습을 이어갈 수 있다. 사용자가 별도로 요청하지 않는 한 라우터 개발·배포·사이트 운영을 학습자 과제로 옮기지 않는다. 입력 준비만 요청받았을 때 알고리즘 본문까지 작성하지 않는다.

## 실제 요청에 대한 응답 기준

| 사용자 요청 | 설계한 응답 행동 | 피할 결과 |
| --- | --- | --- |
| `완료` | 최신 코드와 필요한 실행을 확인하고 이번 완료 기준에 맞는 피드백을 준다. | 코드 확인 없이 숙달 판정하거나 이미 한 과제를 처음부터 반복시킴. |
| `WA 나는 이유` | 접근·반례·첫 잘못된 상태/전이·수정 방향을 연결해 설명한다. | 정답 코드만 덮어쓰거나 사소한 수정을 여러 턴으로 나눔. |
| `이해가 안 돼` | 현재 병목을 확인하고 작은 표·시간표·이동 예시로 설명을 바꾼다. | 같은 설명 반복, 설명 전 퀴즈, 관련 없는 선수 학습 확대. |
| `모범 코드 적어줘` | 요청한 코드를 제공하고 핵심 흐름과 도움 범위를 밝힌다. | 요청 거절, 독립 해결로 기록, 강제 재시험 추가. |
| `코드가 깔끔한가` | 정확성·읽기 쉬운 흐름에 필요한 소수 수정만 검토한다. | 일반 풀이를 서비스 코드 수준의 구조로 개편. |
| `입력 같은 것만 세팅해줘` | 입력·빈 시그니처·실행 연결 중 요청한 준비만 한다. | 학습자가 구현할 본문을 미리 완성. |
| `다음` | 현재 근거에 맞는 과제 하나와 이유·완료 기준을 제시한다. | 이전 도움을 감추고 무조건 난도를 올리거나 복습을 강제. |
| `학습 중단` | 과제 부여와 학습 질문을 멈춘다. 재개 위치 저장은 확인된 위임 범위에서 한다. | 중단 중 퀴즈·새 과제·복습 숙제 부여. |

예를 들어 Crystal Switches 리뷰에서는 무료 전환을 덱 앞에 둔 구현은 맞았음을 먼저 인정한다. 이어 이동할 때 도착 정점의 거리를 갱신해야 한다는 뜻과 반대 방향 간선의 작은 사례를 함께 다룬다. 이 결과를 0-1 BFS 전체를 모른다는 진단으로 바꾸지 않는다.

## 개선 여부를 관찰하는 방법

운영 반영 뒤 다음 네 번의 실제 학습 회차와 로드맵이 정한 다음 정기 측정 기회에서 확인한다. 네 회차는 작은 시범 단위이며 교육 효과를 통계적으로 입증하는 표본 수가 아니다. 지금부터 새 숙제나 대회 일정을 생성하지 않는다.

| 관찰할 내용 | 확인 방법 | 조정 방향 |
| --- | --- | --- |
| 설명 뒤 독립 작업으로 돌아가는가 | 같은 내용을 작은 확인 질문으로 계속 이어가는지, 전체 구현·실행을 맡겼는지 본다. | 불필요한 왕복이 이어지면 설명을 한 묶음으로 줄이고 표현을 바꾼다. |
| 배운 것을 스스로 선택·구성하는가 | 예정된 혼합·재현 활동에서 도움 전 접근, 핵심 도움의 종류, 직접 구현을 본다. | 반복 공백만 보완한다. 충분하면 다음 범위로 이동한다. |
| 같은 의미의 오류가 반복되는가 | 거리의 갱신 대상·후보 자격·값의 보정처럼 원인 단위로 본다. | 새 이론 추가보다 해당 상태·불변식과 코드의 대응을 보완한다. |
| 실제 시간과 부담은 적절한가 | 확인 가능한 학습·독립 시간과 사용자 부담을 기존 예산에 대조한다. | 예산 초과·복습 누적이면 새 분량을 줄인다. 미측정은 추정치로 채우지 않는다. |

문제별 난도·사전 노출·받은 도움이 달라 단순한 AC 개수나 성공률 전후 비교로 개선 효과를 단정하지 않는다. 초기 관찰로 비교할 것은 비슷한 선수와 학습 목표에서 필요한 도움, 반복 오류, 독립 작업 기회의 변화다. rating·실전 성과는 별도의 장기 결과로 본다.

관찰은 강사가 코드와 대화에서 정리한다. 새로운 진도 DB·필수 점수·도움 등급·매회 설문을 만들지 않는다. 기록은 현재 요청 또는 확인된 위임 범위에서 기존 문제 노트와 짧은 STATE를 활용한다. 온라인 판정과 도움의 기존 구분을 재사용한다.

| [참고 자료](REFERENCES.md) | 채택한 연구의 역할과 적용 한계를 짧게 연결한다. | 공식 학습 자료와 날짜가 있는 과거 계정 근거. |

문제·개념 노트, 설정, 제출 코드, 테스트 도구를 일괄 개편할 필요는 없다. 커밋·원격 반영·온라인 제출은 설계 작성과 별도의 요청 범위다.

## 적용 전 검토할 상황

아래는 적용 전부터 정한 강사의 대응 검토 사례다. 실제 응답 검토 결과는 [구현 계획](TEACHING_IMPLEMENTATION_PLAN.md#실행-결과)에 있으며, 학습자의 독립 수행이나 개선 효과를 검증한 결과는 아니다.

| 상황 | 설계가 만족해야 할 행동 |
| --- | --- |
| 새 기법을 처음 배우는데 접근을 떠올리지 못함 | 필요한 설명을 먼저 제공한다. 모든 새 기법의 독립 발견을 입장 조건으로 삼지 않는다. |
| 이미 맞는 코드와 설명이 있음 | 확인한 근거를 재사용하고 같은 기초 퀴즈를 반복하지 않는다. |
| 한 줄 오류가 현재 수업의 불변식임 | 작다는 이유로 설명 없이 넘기지 않는다. 기존 수정 위임도 존중한다. |
| 모범 코드를 요청함 | 제공하고 도움 범위를 구분한다. 과도한 힌트 절차를 강제하지 않는다. |
| AC 보고 뒤 다음으로 이동 요청 | 성과를 인정하고 진행한다. 모든 문제의 백지 재풀이를 요구하지 않는다. |
| 혼합 연습의 실행 파일을 준비함 | 강사가 추가한 설명·함수명·주석으로 추천 기법을 미리 노출하지 않는다. |
| 학습자와 강사가 같은 파일을 수정 중임 | 최신 내용을 재확인하고 원본을 덮어쓰지 않는다. |
| 대회·복습 때문에 주간 예산을 넘길 예정임 | 다른 활동을 대체하거나 신규 분량을 줄인다. |
| 사용자가 수업 점검을 위해 학습을 중단함 | 점검·설계만 수행한다. 새 연습을 이어서 부여하지 않는다. |

문서의 구조와 링크 검증은 이 설계가 읽히고 연결된다는 확인이다. 수업 개선 여부는 사용자가 재개한 뒤 위 관찰로 확인해야 한다.
