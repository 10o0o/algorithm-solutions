## 개요

기존 풀이·노트·환경을 유지하면서 학습 문서와 스킬을 개편한다. 주제를 선택하고 필요한 선수만 보완한 뒤, 주제 내 기초·응용·심화로 난도를 올리고 이후 다시 방문한다. 주 5–7시간 안에 설명·독립 작업·복기·기록을 모두 배치한다. AtCoder 파랑 1600 → 노랑 2000, ABC 실전 올솔, 장기 Codeforces 빨강 2400+는 별도 목표다.

현재 SCC·축약 그래프 구현에서 남은 DAG DP 연결을 이어간다. 이미 구현한 SCC를 재개 관문으로 반복시키지 않고, 미구현 과제를 완료로 기록하지 않는다. 설계 근거는 [연구 결과](research.md), 기록 개념은 [데이터 모델](data-model.md), 실제 적용 검증은 [검증 가이드](quickstart.md)에 둔다. 계획 작성 단계에서는 설계까지만 수행했고, 승인 후 실제 학습 운영 기준은 [ROADMAP](../../ROADMAP.md)에 반영했다.

연구 전 질문은 문서 책임·과거 이력 보존·독립 시간 산정·기록 호환성이었다. [연구 R01–R08](research.md)에서 선택과 대안을 정리했다. 설계를 차단하는 미해결 질문은 없다. F/G 노출·도움·Codeforces 현재 rating·사용자 독립 재현은 미확인 자료로 유지한다.

## 헌법과 적용 지침 점검

[헌법](../../.specify/memory/constitution.md)은 미비준 placeholder 템플릿이다. 예시 원칙·날짜로 준수 판정을 만들거나 이번 계획에서 비준하지 않는다. 아래는 실제 [AGENTS](../../AGENTS.md), [학습 스킬](../../.agents/skills/study-algorithms/SKILL.md), 승인 명세에 대한 점검이며 헌법 비준·준수 인증이 아니다.

| 게이트 | Phase 0 진입 전 | Phase 1 설계 후 |
| --- | --- | --- |
| 명세 승인 | Run의 `review-spec` 결과 `approve` 확인 | 승인된 범위·26개 FR 유지 |
| 단계 경계 | 계획 산출물만 작성 | 작업 분해·운영 반영은 `review-plan` 승인 뒤로 남김 |
| 학습자 소유권 | 코드 읽기만 수행 | 독립 구현·요청형 도움·진행 중 측정 도움 제한을 계약으로 정의 |
| 증거와 기록 | 계획·샘플·AC·도움·재현을 분리 | 독립 작업 시간과 독립 해결 성과도 분리 |

| 보존 | 기존 파일 해시·상태 확인 | 기존 문서·노트·코드·scratch를 이번 단계에서 수정하지 않음 |

| 범위 | 새 서비스·원격 작업 제외 | DB·수집기·새 회귀 테스트·커밋·push·제출·배포 추가 없음 |

학습·범위·단계 게이트에 미해결 위반은 없다. 기존 단위 검사의 별도 실패는 아래에 명시하며 전체 저장소 검증 통과라고 보고하지 않는다. 확장 설정은 사전·사후 점검에서 없었다. 계획 품질 통과는 사용자 `review-plan` 승인을 대신하지 않는다.

### 주제별 진행과 처음 4주

T01–T13의 상세 알고리즘 범위는 [승인 명세](spec.md)를 설계 근거로 삼아 ROADMAP에 반영한다. [회차 계약](contracts/learning-session.md)은 주제별 진입·변형·재방문 관찰 기준을 설명하는 계획 자료이며, 개편 적용 후 실제 학습 범위와 운영의 기준 위치는 ROADMAP이다. 선수 관계는 과제마다 필요한 갈래만 적용한다. 모든 기초를 다 마쳐야 응용에 들어갈 수 있다는 공통 관문은 없다.

첫 4주는 ① 현재 SCC → DAG DP 연결, ② 관찰한 공백에 맞는 DP 응용, ③ 이분탐색 응용, ④ 태그 없는 혼합 점검과 운영 검토를 기본으로 한다. 대회 주에는 해당 주의 활동을 대체한다. 과제가 이어지면 다음 신규 범위를 줄이고 시범 시작일·실제 수행·미실행을 구분한다.

4주 검토는 실제 시간·도움·반복 오류·지연 재현과 미확인을 보고 유지·축소·상향 중 하나를 정한다. rating·올솔 달성은 4주 완료 조건이 아니다. 이후에도 4주 단위로 조정한다.

### 증거와 문서 인터페이스

[데이터 모델](data-model.md)은 주제·과제·시도 증거·재현·예산·목표 결과의 관계를 설명하는 개념 모델이다. 파일 생성 규칙이나 DB 스키마가 아니다. [기록 계약](contracts/document-records.md)이 기존 frontmatter와 본문·상대 링크·저장 요청 범위를 정한다.

새 기법에는 필요한 설명과 작은 예제를 주고 사용자가 직접 작업한다. 혼합 점검은 접근법을 숨긴다. 실전·측정용 virtual 중 도움을 요청하면 종료 후 복기로 안내하고, 도움을 받은 virtual은 일반 연습으로 구분한다. 과제의 도움과 결과는 노트의 사실로 남기며 전체 주제의 단일 ‘완료’로 압축하지 않는다.

기존 노트 검사는 메타데이터·링크의 회귀를 확인한다. 문서 시나리오는 개편 설계의 의미를 확인한다. 둘 다 사용자 숙달·실제 대회 AC·시범 운영 성과를 증명하지 않는다. 웹 코드·콘텐츠를 바꾸지 않는 이번 계획에서는 웹 빌드가 필요하지 않다. 후속 구현이 공개 학습 노트까지 변경되면 [웹 검증](../../docs/WEB.md)을 추가한다.

## 검증 중 확인한 기존 실패

계획 작성 중 내부 제한 환경의 단위 검사는 49개 중 46개 통과·1개 실패·소켓 제한으로 2개 건너뜀이었다. 이후 기본 협업 환경의 구현 검증에서는 소켓 검사도 통과해 **48개 통과·같은 1개 실패·건너뜀 0개**를 확인했다. 실패한 [라우터 설정 검사](../../tests/test_companion_router.py)는 VS Code 작업이 한 개라고 가정하지만 현재 [작업 설정](../../.vscode/tasks.json)은 Companion 작업 하나와 공식 Spec Kit 작업 네 개를 포함한다. 해당 두 파일이 작업 전부터 현재 HEAD와 동일함을 내용 해시로 대조했다. 이번 개편이 만든 회귀가 아니며 승인 범위에 따라 원본을 보존했다.

계획 당시 노트 10개 검사, lock 검사, 새 설계 문서 6개의 링크·예산·요구사항 연결 검사는 통과했다. 최종 구현 검증은 검증 가이드의 실행 기록을 따르며, 기존 실패와 변경 없는 웹 검사·실제 학습 시범 미실행을 구분한다. 향후 도구 검사 자체를 수정할 경우 별도 작업 범위로 다루며 이번 여덟 문서 개편에는 포함하지 않는다.

## 완료와 다음 검토

이 단계의 완료 조건은 연구 질문 해소, 개념 모델·두 문서 계약·검증 가이드 작성, 적용 지침 재점검, 기존 자료 보존 확인이다. 실제 검사 결과와 미실행 범위는 [검증 가이드의 실행 기록](quickstart.md#이번-계획-단계의-실행-기록)에 남긴다.

공식 `review-plan`의 명시 승인 후에만 작업 분해와 구현으로 진행했다. 계획 품질 검사·이 문서 작성·명세 승인을 계획 승인으로 대체하지 않았다. 2026-10-19 KST 사용자의 “승인할게. 진행해”와 `paused`·`review-plan` 조회 후 같은 Run을 재개했다. 복구 과정에서도 기존 승인·요구사항·Run ID를 유지했으며 최종 `status`에서 전체 실행과 여섯 단계의 `completed`를 확인했다. 실제 4주 시범·DAG DP 풀이와 원격 반영은 별도다.
