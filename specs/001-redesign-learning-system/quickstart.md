## 전제와 준비

저장소 루트에서 실행한다. 기존 환경은 uv·CPython 3.12이고 검사 의존성은 lockfile에 있다. 환경이 없을 때만 다음으로 준비한다.

```bash
uv sync --frozen
```

이번 단계는 명세·계획의 명시 승인 후 공식 구현 단계다. 변경 범위는 승인된 운영 문서 여덟 개와 이 가이드·작업 완료 표시다. 검증 전에 사용자 변경과 현재 단계를 확인한다.

```bash
git status --short --branch
bash scripts/speckit-workflow.sh status 1d02e086
bash .specify/scripts/bash/check-prerequisites.sh --json --paths-only
```

기대 결과: 실제 브랜치는 `main`, 기능 디렉터리는 `specs/001-redesign-learning-system`이다. `review-spec`·`review-plan`·`tasks`의 완료와 현재 `implement` 상태는 실제 조회값으로 구분한다. 기존 승인 근거는 [명세](spec.md)와 [계획](plan.md)에 있다. 기능 식별자가 Git 브랜치 이름처럼 출력될 수 있으므로 실제 브랜치를 별도로 확인한다. 실행 중인 Run을 새로 `run`/`resume`하지 않는다.

## 자동 검사와 문서 검사

```bash
uv run --frozen python -m unittest discover -s tests -v
uv run --frozen python scripts/validate_notes.py
uv lock --check
git diff --check
```

검사별 실제 결과를 보고하고 lock 변경·공백 오류·회귀 여부를 확인한다. 하단 기록의 기존 라우터 검사 실패를 전체 통과로 숨기거나 문서 계획 범위를 넘어 수정하지 않는다. 기본 노트 검사는 `knowledge/`, `contests/`, 플랫폼 노트의 기존 메타데이터·링크를 확인한다. 일반 문서·스킬·Spec Kit 산출물은 그 스키마의 대상이 아니므로 이 검사만으로 새 계획 문서를 검증했다고 하지 않는다.

설계 문서와 후속 변경 문서는 저장 후 다시 읽는다. CommonMark 파서로 상대 링크의 대상 존재·저장소 안 경로·문서 앵커를 확인하고, 예산 두 표를 합산하며, 아래 시나리오를 계약과 대조한다. 새 상시 검사기나 문서 내용을 복제한 회귀 테스트는 추가하지 않는다.
